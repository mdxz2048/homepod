## 已审旧链路与必须分开的语义

已读streaming.py、source.py、session.py、timing.py及Process Tap平台模块。旧BoundedHub、StreamingSource、SessionPatches均具有有限total_frames、duration、自然EOF和尾部padding完成假设，不能用极大total_frames或重复短play伪装无限持续流。新适配必须独立表达未知时长与显式stop，不改冻结核心/旧文件路径来隐藏回归。

Core播放计划使用宿主单调纳秒；Tap hostTime是mach ticks，sampleTime可能分数/非零。原始capture时钟仅作旁路metadata，媒体first_frame从新epoch0连续累加；不得直接把host ticks/sampleTime塞入core frame或Python monotonic。协议计划presentation与RAOP send origin仍有latency差，真实采集到播放的预算/重采样延迟须明确记录，不能只说同时启动。

## 必需独立门禁

| 门禁 | 独立验收证据 |
|---|---|
| 无默认采集/播放 | 导入、help、建立服务/hello不打开Tap或音箱；仅显式用户动作允许开始 |
| 真正未知时长 | 无伪造total_frames/duration上限；持续多个输入块，不拼接有限play；暂空等待而非返回EOF |
| 协议边界 | 版本、session、序号、格式、payload帧/字节严格校验；分片及多个帧合包正确；行/帧/缓冲上限明确 |
| 原生参与 | 标准PCM逐块经过实际C ABI/核心分路，输出内容与哈希/帧数证据，不能Python旁路分轨 |
| 时间域 | capture原始metadata保留，显式epoch/first_frame/presentation映射与格式/时钟变化策略；迟到不悄悄重算单路起点 |
| 有界全组 | 输入队列、每路输出和未消费首块常驻预算；异速消费和满队列超时fail-stop；不静默丢帧仍称正常 |
| EOF异常 | 采集主机退出/断管或不完整帧不是自然文件完成，必须全组失败/清理，不无限补零或宣布completed |
| stop可控 | 无限输入下显式stop唤醒所有等待者，阻止新输入，再清理发送/Tap/进程；无可靠清理证据则失败/poison |
| 会话隔离 | 旧session/迟到数据/事件不能污染重启后的会话；epoch跳变按契约明确拒绝或重建 |
| 排除反馈 | 实际App/采集host/发送worker PID排除有证据；PID变化先停并更新，不能用陈旧排除继续捕获 |
| 诚实结论 | mock/离线、真实Tap有声采集、真实多音箱出声、声学同步分别记录，不互相替代 |

## 本轮独立审核与修复复核

已审 LIVE_PCM_PROTOCOL_V1 与新增 adapters/live/{hub,pcm,capture,session}.py、adapters/system_worker.py。未知长度源不以巨大的有限 total_frames 代替；临时暂空等待且显式 stop 唤醒等待者，意外结束失败。首 PCM 接收单调时间 R0 与原始 mach 时钟分开；共同计划为 P0=R0+协议 latency+500ms、S0=R0+500ms，启动不足或迟到整组失败。此映射不包含尚未量化的采集/转换/IPC 延迟。

独立发现并通知 owner 后，已复核以下修复：

- 输入首块部分消费仍按完整驻留数组计入预算；原先逻辑剩余帧记账可让常驻输入超过预算，独立反例已覆盖。
- stopped 回包除了 cleanupComplete，还必须提供 drainComplete=false 和布尔 discardedConverterTail，避免把未知转换尾部伪装成已排空。
- 停止捕获、停止 hub、取消发送/关闭连接并发进行，不先等待捕获退出数秒才停止发送。
- sender 清理未确认时不在旧任务仍运行期间恢复全局 pyatv 补丁；专用 worker 必须保持 poison、退出后才能重新使用。

## 2026-11-06 零 PCM 排障独立复核

总协调转述真实 probe 已取得 48000Hz Float32 stereo 格式、3 秒没有错误但没有音频块，用户未见权限提示。该轮原始报告尚未落入本 QA 可审核目录，因此不将转述作为独立验收通过证据。

代码可证明的事实：HALCaptureBackend 安装非捕获 C IOProc，回调直接调用 C ring，不向 MainActor dispatch；CaptureSource 在 MainActor 上消费，probe 与 host 空读后均 await Task.sleep(2ms)，没有发现消费循环同步占据 MainActor 导致回调无法执行的证据。AudioDeviceStart 成功后只代表启动调用 noErr，ready 发出不要求收到 PCM。

关键观测缺口：CaptureRing.c 对 mDataByteSize==0 直接返回，不入队。probe.blocks 统计的是成功 readBlock 数，而不是 IOProc 次数。因此 blocks=0 应写“没有可消费 PCM 块”，不能写“回调完全没发生”。应由实现 owner 增加无锁调用次数、空输入次数、有效入队次数及 fault 计数，消费端读取，避免在 RT 回调打印日志。

建议由总协调按顺序取证：

1. 保留原失败报告；在明确有未被排除的本地播放器输出时重复短 probe，记录播放器 PID、排除 PID 与实际输出设备。沉默窗口的零块不能直接定位权限或 HAL 错误。
2. 读取当前默认输出、tap/aggregate 输入流和 running 状态。现实现 aggregate 只有 tap list，未配置物理 subdevice/显式 clock；这只是拓扑核对点，尚不能判为根因，不应直接改变用户路由。
3. 使用调用/空 buffer/入队计数区分 HAL 未回调、回调无输入和消费端问题，再针对对应层调查。
4. 权限继续标 not_inferred。未出现提示、CreateTap/AudioDeviceStart noErr 都不能单独证明批准或拒绝；可比对同一签名 bundle 在登录桌面的显式执行结果，不先重置用户 TCC。

新增停止测试确认：只有 HPCM 停止回包 cleanupComplete=true 且 host 实际 exit0 同时成立才标清理成功；ack=false 或 exit7 必须保留失败。该测试仍是内存假进程，不能代替 HAL 实际清理证明。

### 未注册排除 PID 的新阻断及策略门槛

总协调随后转述 rootcapture-real-third 明确失败于 NoCoreAudioProcessObject（Python worker PID 22763），cleanupReported=true，尚未到授权环节。这一轮已知原因与先前零 PCM 现象应分别记录，不能把本轮错误归因于权限。原始日志仍待回传。

正在实现的策略仅可用于 exclusive 的排除列表：当 PID 明确存活，且 Core Audio 翻译返回 noErr 与 Unknown 时，可记录为 notRegistered 受监控项，而不是宣称已排除某个不存在的 AudioObject。正向 include 未注册 PID 仍须拒绝；任意非 noErr 错误、不可确认存活、监听安装失败都不能静默转成全系统捕获。

必要门槛：安装 processObjectList listener 前后双检，启动 IO 前再次检查；watch PID 一旦注册，立即标 callback fault，消费端在释放 PCM 前检查并全组停止。停止过程中必须移除/排空监听，失败沿用 cleanupUnconfirmed。报告记录 notRegistered PID 与实际排除 AudioObject，不能把两者合并成“全部排除成功”。PID 消失/复用也不能静默继承旧进程的豁免。

此策略存在异步观察边界：系统进程注册到 listener 执行及 fault 被消费之间存在窗口，不是“物理上绝无一帧反馈”的证明。代码可减少窗口但不能由单元测试证明绝对零泄漏；若产品需要绝对保证，仍需更强的系统级隔离或其他明确可靠的机制。目前仅为待实现/待 Mac 验证的有边界方案，不作为真实排除实效通过。

### 最终源码门禁复核与终端错误清理差异

已只读复核落地的 ProcessExclusionPolicy、HALCaptureBackend、ProcessIdentity.c：仅 exclusive+noErr+可验证 birthtime identity 的 Unknown 可以进入 notRegistered；include Unknown 拒绝。解析时前后核对身份；所有排除项安装监听前后、start 前后复查，process-list listener 加 100ms timer 观察 object/identity 变化并 fault-stop。ready.exclusionPolicy 分列实际排除对象与未注册 PID；未发现违反上述方案的 P0 源码阻断，实际监听触发和清理仍等待 Mac 证据。

RingToken 的 NSLock 仅位于非 RT listener/timer 路径，IOProc 不取得该锁。setFault 与 invalidate 使用同一锁，晚到事件不能在 token 失效后访问 ring；查询进程的闭包先读 isActive 后虽可继续完成查询，最终 setFault 仍再次受锁保护。只有 stop、IOProc 销毁、监听移除确认后才 invalidate 并释放 ring；清理失败继续保留存储。这是源码所有权审核，不替代调度压力实测。

CaptureHost 新增终端 error 清理分支的语义合理：与当前 start/session 严格关联的 error 帧明确 cleanupComplete=true，且宿主以约定错误 exit3 退出时，可以确认资源已清理；采集操作仍失败，不能改报成功。新增独立差异测试验证 ack=true/exit3、ack=true/exit0、ack=false/exit3、旧session/exit3 四组合，均保留 ready/stopped 的 LiveFailure 与 hub.fail，仅第一种允许资源 clean。
