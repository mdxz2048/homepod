# 虚拟音频入口：首轮工作流与验收

日期：2026-11-06。用户明确授权先备份当前代码，再由总协调安排开发。备份是开发快照，不是正式版发布。本文先固定分工与门槛；GitHub远端确认后再开始本阶段实现派工。

## 首个目标

一个立体声虚拟输出设备接收普通应用声音，沿现有系统采集/核心/AirPlay链路送至HomePod；正确提供实际呈现延迟，验证浏览器是否自动补偿画面。先验证该机制，不以“有延迟属性”或“界面出现虚拟设备”宣布音画同步完成。暂不同时实现完整5.1/7.1与全部播放器适配。

保留现有Tap兜底及动态音量，不改冻结C ABI v1和35个保护文件。新增输入/驱动/控制独立封装。多声道格式契约需预留真实rate/channel labels/provenance，但当前实现只承诺实测立体声；文件仍由外部播放器播放，不新增产品文件入口。

## 第一轮边界

- driver：使用公开Audio Server Plug-in机制，先提供Float32 stereo、44100/48000Hz能力、正确稳定时钟和属性，不使用内核扩展。不得假报尚未实现的多声道。
- 输入：优先验证虚拟输出配合受支持的device/stream Tap能否取得真实PCM、无需新增麦克风权限；若不成立，再评估驱动loopback输入或有界共享传输。确定前禁止各模块各自发明另一套不可兼容数据协议。
- 延迟：device/stream延迟、AudioUnit及hostTime如何组合必须明确；整组实际输出预算稳定，上报只记一次，变化要通知且核对客户端是否需重开流。禁止更改苹果内置设备latency、通过虚假时间戳冒充未来声音或固定填2秒后称已校准。
- 系统所有权：默认输出切换/恢复独立controller；准备前保存原设备与所有权，用户随后修改优先。App关闭、失败、驱动不可用必须有恢复策略。代码先构建为可审查产物，不自动安装到系统HAL目录、重启、杀coreaudiod、改变信任或绕过TCC。
- UI：沿用单布局与两模式，默认自动选可用输入；诊断信息不增加到正常操作流程。当前默认输出由用户原生选择的HomePod不得被开发脚本静默覆盖。

## 依次验收

1. 源码可构建、可查验签名/权限和卸载路径；驱动API及RT路径独立审查，无阻塞/文件网络操作。
2. 安装后系统能枚举，声明格式均真实可用，启停不崩溃、无失控系统静音，移除/故障可恢复输出。
3. 外部应用实际立体声→虚拟设备→捕获→现有两台HomePod，计数/非零/有界/清理与音量均验证；不把直接文件推送当此项。
4. 上报准确可控延迟，并验证Chrome/Safari及至少一个播放器是否采用；用已知闪光/脉冲素材同步拍摄或受控测量记录真实偏差，包含暂停、seek、重开输出。
5. 再扩展真实六声道输入和标签映射；原生pair/多声道等历史需求不因当前切片被默默删除。

本阶段目标是可证伪地验证自动音画路径；若某浏览器不采用延迟，保留结果与兼容范围，才转播放器适配，不伪报所有来源自动同步。
