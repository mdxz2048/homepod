# 多 Agent 开发工作流

日期：2026-11-05。适用范围：HomePod Spatial Router 的设计、实现、集成和验证。本文规定执行方式，不表示任务已开始或功能已实现。

## 1. 组织方式

总协调 Agent 负责拆任务、派工、依赖、工作区隔离、状态收敛与集成。设置六类专业角色：产品设计、技术架构、SwiftUI 设计实现、App 逻辑开发、底层核心开发、独立验收。

角色是长期责任，并不要求六个角色始终各占一个运行进程。当前会话支持总计四个并发 Agent，因此通常由协调者 + 三个工作 Agent 运行；专业角色按阶段进入执行。后续并发额度允许时，可以保持相同规则扩展。

角色身份与任务标识必须记在任务文档中。上下文通过文档恢复，避免依赖某个 Agent 一直存活。暂停/更换执行者时先写交接，未完成操作和运行进程需要交代清楚。

## 2. 角色与决策权

| 角色 | 负责与交付 | 决策边界 |
|---|---|---|
| 总协调 | 任务图、派工、冲突调度、集成记录、用户进展 | 执行顺序和工作区；不能自行降低产品/验收条件 |
| 产品设计 | PRODUCT、正常/异常用户流程、功能边界、UI 易用性审核 | 用户可见行为；与架构共同收敛范围 |
| 技术架构 | ARCHITECTURE、契约、ADR、依赖规则、技术审核 | 公共接口、模块依赖、跨平台边界；不得无记录删除需求 |
| UI Swift | UI 规范、SwiftUI 视图、组件、交互预览与所有状态表现 | 视觉和视图实现；消费状态模型，不实现网络和同步逻辑 |
| App 逻辑 | 平台捕获适配、权限、应用生命周期、ViewModel、核心绑定和配置持久化 | 平台产品层；不在 Swift 界面层复制核心同步算法 |
| 底层核心 | 跨平台音频模型、Router、SyncCoordinator、PlaybackEngine、传输适配 | 按批准接口实现；接口改动先提案，不静默改变语义 |
| 验收 | 早期验收设计、模拟测试、跨模块/真机验证、缺陷、复测与报告 | 独立给出通过/失败/未验证；不替开发者隐瞒失败 |

产品与架构发生冲突，先给出可验证事实、影响和替代方案。可在已授权目标内解决的由双方记录共同决策；影响用户核心目标且无法兼容的，再由协调者向用户集中说明并求取必要选择。

## 3. 代码与文档归属

建议代码目录随实施逐步建立：

| 路径/对象 | 默认写入负责人 |
|---|---|
| `apps/macos/.../Views/`、`Components/`、视觉资源 | UI |
| `apps/macos/.../App/`、`ViewModels/`、`Services/` | App 逻辑 |
| `bindings/swift/`、`adapters/capture-macos/` | App 逻辑 |
| `core/` 的私有实现、AirPlay/文件/测试源适配实现 | 底层 |
| `core/include/hsr/` 公共接口、顶层构建/依赖规则 | 架构 |
| XcodeGen 工程定义、App 入口和组装 | App 逻辑 |
| 验收目录和集成/契约测试 | 验收；任务可明确授权开发者补充指定测试文件 |
| 产品、UI、架构、验收权威文档 | 各对应角色 |
| TASKS、任务分派和集成记录 | 协调 |

该表是默认责任分配，真正写入前任务卡必须列出具体文件范围。公共接口文件可以由架构批准后交给底层实现者修改，但同一时段只允许一个任务拥有写入权。模块内部构建文件由模块实现者负责，顶层与工程文件避免多人同时改。

建议每个实现任务使用隔离分支/工作树，分支前缀 `codex/`。任务开始前确定基线提交和依赖版本。尚无初始提交的仓库，先由协调者记录并建立干净基线，再分出任务分支。隔离工作树仍需遵守文件责任，不能以最终能够合并为理由同时重写公共文件。

协调者逐个集成已通过审核的改动，在合并后的实际组合上验证。修冲突后必须重跑受影响检查；开发分支通过不等于组合通过。

## 4. 统一交接格式

每个任务建立 `tasks/TASK-xxx.md`，协调者创建和分配；任务执行期间由被分配角色维护正文，协调者维护 TASKS 索引。其他角色通过工具消息提出问题，最终结论由任务所有者记录。交接最少包括：

```text
任务 ID / 标题 / 当前执行角色
输入基线：提交、需求 ID、契约版本、依赖任务
目标与范围：做什么，明确排除什么
允许修改的文件/目录
交付物：源码、设计、预览或证据路径
通过条件：可执行检查及用户可见行为
结果：完成项、验证命令和结果、未完成项
影响：公共行为/接口/依赖是否改变
阻塞：原因、影响任务、所需决策
交接：提交/补丁、下一位审核角色、环境和运行进程
```

消息用于即时通知，权威结论写入文档后才算交接完成。避免复制同一结论到多个文件反复维护；使用 ID 和链接引用。截图、录音和大日志存证据目录，文档只保存索引、环境和结论；不提交凭据。

## 5. 状态与审核

任务状态：Backlog → Ready → In Progress → Review → Verified → Integrated。

- Ready：输入明确、依赖满足、文件责任已分配；可使用已批准的模拟接口开始。
- Review：实现者提交具体改动、验证结果与交接记录。
- Verified：技术审核和适用的独立验收通过；UI 任务还需产品流程审核及视觉检查。
- Integrated：协调者合入目标基线，组合验证通过并更新索引。
- Blocked：注明真实阻塞、责任人和可继续的其他工作；不能把未验证写成通过。

开发者负责自检，技术架构检查边界与实现，验收 Agent 独立复核。协调者不能仅凭“Agent 已完成”就标记 Integrated。纯文档/低影响视觉调整采用相称的检查；同步、队列、恢复与捕获需要有行为证据。

## 6. 接口先行与版本控制

产品先定义用户行为，架构给出最小接口和完整语义，UI/App/底层/验收再基于同一版本同步实现。无需等全部产品设计完成，只冻结当前切片所需契约。

第一批必须明确：AudioBlock、时钟/媒体时间、设备标识、能力、Transport、PlaybackEngine、App 展示状态。说明所有权、线程、生命周期、取消、背压、失败、恢复和支持范围。只列函数名不算契约完成。

公共接口变更流程：提出 CHG → 架构列出影响 → 产品确认用户行为变化（如有）→ 更新契约版本/决策 → 协调者生成迁移任务 → 提供方、调用方和测试在同一集成批次更新。

未批准的破坏性改动不能直接进入主线。旧调用方未迁移时使用明确的适配层；模拟实现也必须通过相同契约检查。依赖库升级单独派工，记录能力和兼容性验证。

## 7. 并行节奏

### 阶段 0：共同设计输入

协调 + 产品 + 架构 + 验收：产品收敛首版；架构形成接口草案；验收提前把要求转为用例与证据条件。设计分歧在进入实现前收敛。

交付：首版范围、最小用户流程、批准契约、验收矩阵。对尚未通过的捕获/视频/同步能力保留实验任务，不以设计代替可行性证据。

### 阶段 1：三条实现线

协调 + UI + App + 底层：

- UI 使用预先定义的状态和模拟数据，实现连接、播放、离线、恢复、权限缺失等界面。
- App 使用模拟 PlaybackEngine，实现权限、设置、平台生命周期和状态绑定；同时开展真实捕获实验。
- 底层使用文件/测试源和模拟输出，实现跨平台核心，再接入现有 AirPlay 方案。

契约问题提交给架构角色；需要执行架构审核时切换一个运行槽位。验收规范已在前一阶段确定，开发者持续按其自检。

### 阶段 2：频繁集成

按可运行切片集成，第一条为“选择已有房间 → 文件/测试源 → 真实三台不同内容播放 → 停止”。之后增加真实应用捕获、连续流、恢复、视频来源能力。

每完成一个可运行切片，协调者优先集成并安排架构/验收复核；避免等 UI、App、底层各自全部完成才首次联调。当前并发槽位可切换为协调 + 架构 + 验收 + 修复负责人。

UI 预览不能证明底层出声，模拟成功不能证明真机通过；完成真实绑定后要复查所有状态和错误路径。

### 阶段 3：独立验收和产品审核

协调 + 验收 + 产品 + 待修复模块负责人：验收回归、产品审功能与界面、实现者修复。出现问题直接派回对应模块；修复后验收复测。架构对涉及公共边界的修复参与审核。

### 阶段 4：可安装交付

打包 App、自包含运行依赖、安装/启动检查、签名与权限行为检查、验收摘要、已知限制及回退版本。没有通过的能力不放进默认可用路径。外部发布按届时用户授权处理，日常开发与本机安装检查无需逐项请求确认。

## 8. 首批切片和任务

1. 建立产品需求 ID、首版范围和验收基线，保留现有成功原型。
2. 批准核心契约，定义模拟引擎/接收端，以及 UI 的状态模型。
3. 并行实现 UI、Mac 应用壳与核心库/现有 AirPlay 适配。
4. 第一条真实三台输出链路集成；在 Mac 重复验证实际出声及不同内容。
5. 持续输入和应用捕获，解决本机重复出声、源中断及时间戳变化。
6. 暂停恢复、断线、唤醒和长时同步验证；按真实能力补全 UI。
7. 可控视频/多声道来源实验和兼容性结果；其关键风险早期研究，不拖到发布前。
8. 可安装版本和阶段验收。

## 9. 自动推进与人工参与

协调者在当前执行期间持续完成拆分、派工、审核、修复、复测和集成，不把常规工程选择交给用户逐项确认。向用户报告已验证成果、风险变化和需要操作的具体事项。

不可由 AI 代替的现场动作可能包括：系统授权、苹果账号认证、确认音箱位置、将录音设备放到座位。真机结果以获得的证据为准；缺少物理设备/测量时仍可完成模拟和代码检查，但不能宣布对应真机条件已通过。

多个测试任务共用一组音箱时，由协调者分配独占测试时段，避免抢连接、音量及录音设备。同理，开发工具路径、Mac 构建目录、应用签名与安装位置由协调者串行安排修改。真机有声测试遵守已有授权，使用任务明确的音量，不沿用历史 100% 测试音量。

本文不代表已建立持续后台执行或定时唤醒。正式启动协作时，按可用执行时段和并发额度运行任务，结束前记录状态和恢复入口。
