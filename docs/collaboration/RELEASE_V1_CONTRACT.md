# HomePod Flow 正式 V1 实施契约

日期：2026-11-06。负责人：总协调；技术架构、应用、底层、UI、独立 QA 按本文协同。状态：实施契约首稿，尚未通过正式版验收。用户要求完成正式功能再推出，不以开发预览作为交付。

## 范围与优先级

用户最新明确覆盖早期交付方案：Mac 系统声音输入；正式界面没有文件播放、音效选择或手工声道矩阵；只提供影院与同步播放两种模式；设置仅一个布局页；菜单按照真实设备型号和保存布局显示。内部 WAV/tone 可保留作回归工具，不成为用户操作步骤。

原需求中的应用选择、原生立体声组合、多声道、布局方案、按应用偏好没有因 UI 简化而自动取消。不能把“隐藏入口”“报告不支持”“换成同声复制”作为完成。必须实现、验证可证替代，或由总协调明确提出范围决定及其依据；无法满足原要求时保留缺口，不能单方面签发完整版。

正式使用应为：启动已安装 App → 首次授权与布局选择 → 菜单选择影院/同步并开启 → 日常应用正常发声 → 全部音箱按共同时间播放 → 直接调音量/共同偏移 → 关闭后无残留采集或发送。首次必要授权需用户操作，正常运行不依赖终端、文件选择、开发路径、Python 安装或逐台延迟调节。

## 模块边界与立即实施顺序

```text
SwiftUI / AppState / SystemAudioStore
  → versioned system worker control
  → TapCaptureHost → HPCM → LiveHub
  → portable processing v1（新增）
  → frozen core C ABI v1（保留）
  → AirPlay adapter → HomePod outputs
```

1. 固定安装身份下完成公开 TCC 授权及真实非零系统 PCM。此项与 DSP、恢复及打包开发并行；不得绕过 TCC。
2. 新增独立 `processing/` 可移植 C++17 库及绑定，负责布局矩阵、平滑增益。旧核心 ABI 和 35 个 M2 保护文件不改。不同功能由不同库负责，不把捕获、Python 或 Swift 对象引入 DSP。
3. worker 接入矩阵输出、运行中音量、共同延迟、全组恢复；App 仅消费能力和确认事件，不能先更新 UI 再假定后端成功。
4. 补齐输出静音/恢复、原生组合和原多声道能力调查与实现、依赖打包，最后以发布包做真机及 UI 独立验收。

当前若冻结核心只支持通道复制，处理库可以一次生成 N 个设备的 2ch 平面，再将其交错为 2N 通道作为现有核心输入，每设备路由到自身两个通道；须验证实际通道上限和内存预算。若超过已支持上限，显式拒绝并报能力不足，不改旧 ABI、截断通道或伪报任意 N。是否采用此桥由底层负责人与总协调在源码中确认。

## processing v1 最低可用契约

输入：固定 44100Hz、有限 Float32 交错立体声；块携带 session/epoch、first_frame 和帧数，连续性由 live 桥校验。输出：每个稳定设备标识独立的两通道内容，帧数、epoch、起止媒体帧完全一致。不增加每路单独时延。接口提供版本、创建/销毁、准备布局、处理块、调度增益更新；名称可由实现者确定，但必须形成头文件与调用示例，不暴露 C++ STL 到跨语言 ABI。

处理路径不得按块分配、访问文件/网络或调用平台 API。矩阵与缓存 prepare 时有界分配；返回明确错误，不接受 NaN/Inf、错误通道或越界帧。控制更新采用单写者/单音频消费者契约或有界命令队列；调用者不得并发读写裸矩阵。所有输出预检容量后才处理并提交同一块，避免只更新部分设备。

### 同步模式

所有设备接收同一 L/R；共同主增益及各设备相对增益在提交同一媒体帧时生效。HomePod 内部的实际立体声重现由设备能力决定，不能将一个物理 HomePod 画成两个可独立控制的扬声器。

### 影院模式：立体声输入的真实边界

目前 Tap stereo 只证明捕获到两通道，不能证明源文件是 2.0，也不能反推出已被系统降混丢失的独立 5.1。此输入的影院必须标注“立体声·空间分配”，不标原生环绕、Atmos、还原后声道或提取独立对白。M/S 相关性只能是保守布局矩阵，不能称人声/环境分离。

建议首版可验证矩阵如下，底层若有更好算法须在实现与验收前更新此节；不得用与同步模式完全相同的内容冒充影院：

- `M=(L+R)/2`，`S=(L-R)/2`。
- 根据听音点、屏幕方向和已保存坐标生成后方权重 `r∈[0,1]`、左右方向 `p∈[-1,1]`（左为 -1，右为 +1）。坐标先归一化，重合/退化布局使用有定义的默认值。
- 后方单设备内容 `Q=0.25*M - 0.70*p*S`；设备两通道 `Yl=(1-r)*L+r*Q`、`Yr=(1-r)*R+r*Q`。正前方 `r=0` 保留 L/R，左右后方产生不同差分响应。mono 时 Q 保留低电平主内容，不能因 L=R 而完全消失。
- 每行系数绝对值之和归一化至不大于 1；主/相对增益限制 0…1。输入幅值≤1 时无矩阵增益引入的削波。峰值保护不能靠硬削波掩盖错误矩阵。
- 如果没有可用前方设备，至少一个覆盖输出强制保留完整 L/R；所有可用输出不得仅播放低电平差分而丢失主体。设备增减后重新计算覆盖，并在共同新会话生效。

这是可听见区别的线性空间分配，不承诺物理房间重建，也不制造原生不存在的环绕信息。后续多声道输入按真实 channel layout 保留 FC/SL/SR 等独立内容；未知布局不能猜通道顺序。

验收：左右单脉冲、mono、反相、静音、峰值、随机有限输入、退化布局、1/2/3/更多设备、关键前方设备缺失；逐路输出与公开矩阵一致。布局变化确实影响矩阵，不仅影响绘图。实际三台不同内容与同步另做声学验收。

### 运行中音量

主音量 0…100 映射软件主 gain 0…1；相对音量同样有限有界，默认 1。保留设备协议音量的稳定基准，避免软件和硬件重复缩放。首次默认仍为低音量，不继承历史 100% 测试值。

运行中更新包含目标值及共同生效媒体帧；至少 20ms（44100Hz 时 882 帧）平滑，不改变帧计数或各路时间线。0 为真静音，恢复使用最近非零用户值。高频拖动只保留有界更新及最后值；接收与实际生效分别报告。设备硬件音量如果另外可调，必须恢复其会话前值或明确保留用户直接修改，不能与软件主增益互相覆盖。

### 共同延迟及音画范围

不可控制的第三方视频无法因本软件而提前获得未来系统音频；AirPlay/采集已有延迟也不能用负数参数消除。已有 ±3500ms UI 不是已实现承诺，禁止让越界或无效果的方向看似可用。

实现第一步是共同额外 holdback `0…3500ms`，单位和文案明确为“声音延后”；所有输出共用同一缓冲预算，显式计入原来 2 秒输入队列之外的驻留总量。若保留双向 UI，必须先预留基准 B，并把可调范围限制为 `[-B,3500ms-B]`；负值只减少额外缓存，显示实际最低端到端延迟。B 会增加所有内容延迟，不能为了画双向滑块默认无故增加数秒。

动态修改 holdback 使用整组停止清理→新 epoch→当前 PCM 重新预缓冲→共同准备恢复；允许明确短暂重启，不能单独调整发送起点、复制旧缓存、缩短某路或伪报无缝。要实现无重启动态调整，需要后续共同速率/过渡算法及独立验收，不能直接跳帧。UI 等待实际生效才显示确认值。

真正把音频相对视频提前，需对所用播放器提供视频延后控制适配。浏览器/任意 App 没有统一公开视频控制接口时，明确显示“此来源只能延后声音”；仍是可用范围边界，不等于原 PRD 双向 A/V 全部完成。原生可控播放器适配是仍需处置的缺口。

## 自动发现、恢复与睡眠

发现与会话身份用稳定设备 identifier，不用 IP 或名称。scan 向后兼容增加 `identifier`，来源为实际设备公开标识；缺失不能伪造稳定 ID。型号使用可信广播/设备信息，未知时允许用户在唯一布局页确认；保留 `model_source=advertised|user_confirmed|unknown`。识别组合还需稳定 group/member 标识及对应能力，不能把两个同名 mini 当原生 pair。

错误事件扩展 `failure_kind`、`retryable`、`cleanup_complete`；缺少肯定清理信息按不安全处理。`network_transient/device_offline/device_address_changed` 可作为可恢复类别；权限、未知采集失败、格式不支持、清理未确认、内部错误不自动重试。现有 v1 会话/命令关联语义不变。

App 保存内存态 desiredEnabled，只有用户显式成功启动后的会话允许自动恢复；停止/退出立即取消重试。仅 `retryable=true AND cleanup_complete=true` 才允许 1/2/4/8/16 秒最多五次退避。每次 fresh scan，以稳定 ID 唯一解析全部启用目标，全部就绪才新 UUID/epoch 整组恢复。清空旧 PCM/命令结果，旧事件不能覆盖新会话。五次后展示失败及重试，不无限后台采集。

睡眠前停止采集/发送并清理，唤醒且网络可用后才按上述用户意图恢复。无法在睡前完成清理时，唤醒不能直接复用旧 sender。源暂停应继续合法静音/无输入状态监控；seek/源变化不可重播旧缓存。设备失联先整组停止再恢复；“不中断其余音箱、单路无缝加入”需要额外算法与验证，不是本方案默认已有。

长期时钟：输入 host ticks、输出媒体帧、接收设备同步时钟三者保留独立意义。现 receipt anchor 及固定转换率不能证明零漂移。必须监控累积相位/队列偏离；有限速率的全组共同自适应重采样或有界全组重启是可实现方案。常规 30 分钟不得靠周期性重启冒充连续稳定；达到阈值 fail-stop 只能保证不持续回声，不能算长期同步通过。

## Mac 本机重复出声与恢复

正式目标是在启用转发时避免 Mac 本机重复声音，关闭/失败后恢复原状态。优先验证公开 Tap 的 mute 行为是否可仅静音被捕获的本机路径且不影响转发；采集库当前 unmuted 不表示该目标已完成。若无法可靠组合，评估私有受控 aggregate/虚拟输出；需要实际兼容性与默认输出恢复测试，不能用修改系统总音量掩盖。

任何需要修改默认输出/mute/音量的方案，必须记录会话前快照及所有权；只恢复自己修改且未被用户随后覆盖的状态，设备移除时选择系统可用默认并提示。stop、错误、host 崩溃、App 退出均恢复；无确认不得显示已恢复。此策略须更新原“绝不修改系统输出”开发约束，并由总协调认可后执行，不能暗中改系统。若仅允许本机继续响，则需明确用户范围决定，不能默认为正式完成。

## 安装、权限与发布门禁

应用打包包括匹配架构的核心及 processing 动态库、签名 TapCaptureHost、可重定位 Python runtime 与固定依赖、许可声明。不得依赖开发用户 venv、Xcode、绝对路径 runtime.json。依赖安全版本固定、私有 pyatv hook 行为测试、退出子进程清理均属于发布内容。最低 macOS 和 arm64/x86_64 支持按实际构建宣布，不宣称未编译架构；无 Developer ID 时仅对本机可用的签名安装路径说明清楚，不能宣称已公证分发。

固定 App 路径与 bundle identity，从登录桌面 App 用户操作发起采集；系统提示及权限页均用公开流程，权限责任归属必须实测。用户列表没有 HomePod Flow 时不能要求打开一个不存在的开关；先修正安装/宿主责任链并用真实 API 请求。禁止修改 TCC 数据库、绕过系统授权或把 ready/TCC 某值当非零采集通过。

独立验收以 `RELEASE_V1_ACCEPTANCE.md` 为执行门禁。确认采用三台任意两台传播校正后 p95≤10ms、最大≤20ms，30分钟相对变化≤5ms作为正式目标；当前不是已通过。先确认录音分离与测量误差足以支撑这些阈值，不能用误差更大的单麦混录给精密数字。真实输入、声学、打包、UI 和恢复门禁全部需对应发布包及源码哈希；离线测试不能代替。

发布前剩余 owner：底层完成 DSP/holdback/长期时钟与真实格式；应用完成控制确认、恢复、依赖与权限；UI 完成单布局/真实型号/状态及手势；QA 独立复核场景和原始证据；总协调解决历史范围缺口并冻结最后发布清单。全部通过后才生成首个正式可用版本并按用户授权提交到 GitHub `origin/main`；README 仅变更记录。当前不标发布通过、不提前备份为正式版。
