## M0 独立验收范围

本轮入口：`tests/core_contract_tests.cpp`（21 个行为组）、`tests/verify_prototype.py`（3 项保护检查）。模拟输出只保存数据，不包含网络、音频设备或发现调用。通过表示软件契约得到离线验证，不表示实际 HomePod 出声同步或 AirPlay 后端已接入。

| 产品需求 | 本轮必须验证 | 通过所需证据 |
|---|---|---|
| CORE-001 | 1/3/5 路均可配置，重复设备标识/实例、空路由、越界路由拒绝 | 测试逐路检查内容与调用次数 |
| CORE-002 | 各路不同内容、重复通道映射、数据副本、共同 epoch/frame | 记录输出样本和元数据，修改输入不影响已接收块 |
| CORE-003 | 共同未来 origin、按帧计划、不依赖提交时刻；缺少定时能力拒绝 | 注入时钟检查精确时间；能力拒绝发生于 prepare 之前 |
| CORE-004 | 部分 prepare/异常清理、非法输入可重试、背压全组 fail-stop、stop/重启/析构 | 故障注入、所有输出关闭及队列清空；时间线保持规则 |
| CORE-005 | 独立 C++17 核心和无界面测试可构建 | 编译与运行日志；目前其他平台运行不自动视为通过 |
| CORE-006 | 原型源文件及历史记录不变、Python 语法与安全导入 | 基线哈希/长度检查、AST 解析、无播放导入 |

背压契约：M0 不支持多路提交的事务回滚；第二路拒绝时第一路可能已接收，故全组关闭并进入 Faulted，禁止直接重试。清空模拟队列不证明现实里已播放的音频可以撤回。

验收范围明确不包括：三台真实音箱播放、声学同步误差和漂移、实际重连、实时安全、性能/内存上限、Mac 捕获、UI、安装包、C ABI、Windows/Linux 原生运行。以上继续保留待验收状态。

执行报告：[M0 独立验收记录](reports/M0-core-acceptance-2026-11-05.md)。

## M1 桥接独立验收（软件离线切片 Pass）

验证链路限定为：版本化 C ABI -> ctypes -> 实际 C++ 路由 -> 自定义 pyatv AudioSource -> 统一计划的发送入口。旧原型独立播放不能作为这条链路通过证据。

独立用例：原生 C ABI 消费者 `tests/bridge_c_contract.c`；Python `test_native_binding.py` 11 项、`test_airplay_timing.py` 6 项、`test_airplay_bridge.py` 3 项、`test_airplay_session.py` 12 项，另保留原型保护 3 项和 M0 C++ 21 组。Python 合计 35 项，其中涉及动态库的测试必须加载实际构建产物，不以 mock 替代 native 路由。

时序采用预计 presentation 减去实际协议 latency 得到发送起点；验证固定锚点、pyatv RTP 映射、准备 guard、迟到拒绝。同组格式/latency 不同拒绝；成功接受或发送不能标 acoustic_sync_verified=true。

独立验收已发现并交 owner 修复：失败构造引发析构 unraisable、同一 Python 输出实例重复绑定、异步 close 异常误报 cleanup_complete。修复后必须复测；完整结果见 [M1 验收记录](reports/M1-airplay-acceptance-2026-11-05.md)。

最终证据已独立审核：Mac 原生 CTest 2/2 Pass（包含 M0 21 组）、Python 新增 32/32 Pass 且 0 skip、CLI 一秒三路实际 native dry-run Pass；另 Windows 原型保护 3/3 Pass。当前 27 文件与本轮持久化基线及 Mac 源包哈希全部一致。三路 native 输出不同，AudioSource 消费后的哈希逐路匹配。结论只覆盖无网络软件桥接；实际设备连接/出声、声学同步和长期漂移仍未验证，M1 整体未通过。
